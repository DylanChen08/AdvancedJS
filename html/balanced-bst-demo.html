平衡二叉树的核心定义

平衡二叉树（AVL Tree）是一种特殊的 二叉搜索树（BST）， 它在 BST 的"左小右大"规则之上，增加了一条约束：

对任意节点：｜左子树高度 − 右子树高度｜ ≤ 1

这条约束保证整棵树的高度维持在 O(log n)， 使得查找、插入、删除都能高效完成。

高度（Height）是什么？

节点的 高度 = 从该节点到其最远叶子节点经过的边数。

叶子节点高度 = 0，空节点高度定义为 −1（便于计算）。

高度示意

逐层解读

节点 1、3、6（叶子）→ 高度 = 0

节点 2（有两个叶子）→ 高度 = 1

节点 4（根）→ 高度 = 2

平衡因子 BF = 左子树高度 − 右子树高度
节点 4：BF = h(左=2的子树高度1) − h(右=6的子树高度0) = 1
｜1｜ ≤ 1 ✓ 满足平衡条件

为什么不平衡会导致性能崩溃？

普通 BST 在最坏情况下（顺序插入）会退化成一条 链表， 查找需要逐个遍历所有节点。而平衡树通过维持高度在 O(log n)， 保证了每次操作只需少量比较。

n = 1,000,000 时，退化 BST 需要 1,000,000 次比较， 平衡 BST 只需约 20 次（log₂ 1,000,000 ≈ 20）。

但哈希表不是更快吗？
哈希表查找是 O(1)，但它 不支持范围查询、排序输出。
平衡 BST 的优势在于：查找 + 范围查询 + 排序 + 前后驱查询 都是 O(log n)。
例如数据库索引（B树/B+树就是多叉平衡树的扩展）。

三种常见的平衡二叉树

平衡树有多种实现，它们在"平衡严格程度"和"旋转开销"之间做出不同权衡。

类型平衡条件插入/删除复杂度特点实际应用
AVL 树 所有节点 |BF| ≤ 1（最严格） O(log n) 高度最低，查找最快；插入删除可能触发多次旋转 读多写少场景；部分数据库内部索引
红黑树 最长路径 ≤ 最短路径 × 2（近似平衡） O(log n) 旋转次数少（最多 3 次），插入删除更快 Java TreeMap/TreeSet、C++ std::map、Linux 进程调度
Treap 随机优先级维持期望平衡 期望 O(log n) 实现最简单；结合 BST + 堆性质 竞赛编程、对随机性要求不高的场景

选哪个？一句话决策

查找性能优先

读操作远多于写 → 选 AVL 树

插入删除频繁

写操作多 → 选 红黑树

快速实现

竞赛/原型 → 选 Treap

AVL 旋转概念（维持平衡的手段）

当插入导致某节点 |BF| > 1 时，通过 旋转 来恢复平衡，分四种情况：

LL 型 → 右旋

失衡在左子树的左侧，对失衡节点做一次右旋

RR 型 → 左旋

失衡在右子树的右侧，对失衡节点做一次左旋

LR 型 → 先左旋再右旋

失衡在左子树的右侧，需要两次旋转

RL 型 → 先右旋再左旋

失衡在右子树的左侧，需要两次旋转

旋转操作只改变节点的父子关系，不改变 BST 的左小右大性质，且时间复杂度为 O(1)。
